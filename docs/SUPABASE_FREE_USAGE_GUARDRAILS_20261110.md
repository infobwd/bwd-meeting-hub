## 3. เกณฑ์เตือนและคำสั่งดำเนินการ
ระดับต่อไปนี้คือ **เกณฑ์ภายในทีม** ไม่ใช่เกณฑ์ของ Supabase และยัง **ไม่ใช่ alert ที่ส่งอัตโนมัติ**
- **<70% (ปกติ):** ตรวจ Usage รายสัปดาห์และก่อนการประชุมใหญ่; บันทึก snapshot วัน/รอบการคิดโควตา
- **70–<85% (เตือน):** แจ้งผู้ดูแล, ตรวจหาสาเหตุ, ปรับ pagination, ลดขนาดไฟล์, หยุดฟีเจอร์สิ้นเปลืองที่ไม่จำเป็น
- **85–<95% (เสี่ยง):** ตรวจทุกวัน, งดเพิ่มฟีเจอร์ที่กินโควตา, วางแผนย้ายไฟล์/ปรับสถาปัตยกรรมหรือเสนออัปเกรดก่อนแตะเพดาน
- **>=95% (วิกฤต):** ระงับเฉพาะการอัปโหลดหรือกระบวนการไม่จำเป็น *เมื่อมี fail-safe ที่ทดสอบแล้ว*, แจ้งผู้ดูแลทันที, จัดช่องทางบันทึกงานประชุมที่สำคัญ/ขั้นตอน manual fallback; ห้ามทิ้งงานหรือ silently drop mutations

คำนวณเปอร์เซ็นต์ต่อ **แต่ละมิเตอร์โดยอิสระ** (Database, Storage, Egress cached/uncached, MAU, Realtime, Edge). มิเตอร์ที่ไม่มีเลขสืบยืนยันให้เป็น **Unknown — ต้องตรวจ** ไม่ใช่ 0%. ระดับ 70/85/95 ใช้สำหรับ planning ไม่สั่งปิดฟีเจอร์อัตโนมัติในรอบนี้

## 4. แนวทางลดการใช้ทรัพยากรสำหรับ Meeting Hub
1. **ข้อมูลประชุม:** เก็บวาระ/มติ/งานเป็น structured text; ใช้ indexes และ list pagination, ไม่โหลดข้อมูลทุกประชุมทุกครั้ง, ไม่ polling ถี่
2. **ไฟล์แนบ:** Private `meeting-evidence` รับเฉพาะประเภทที่อนุญาตและไม่เกิน 10 MiB; จำกัดจำนวน/ขนาดตามบริบท, บีบอัดรูปก่อนแนบเมื่อเหมาะสม, ห้ามเอาไฟล์จริงไปไว้ public GitHub
3. **ไฟล์ขนาดใหญ่:** พิจารณา Google Drive เป็นที่เก็บเอกสารภายใต้นโยบายสิทธิ์รายประชุม และบันทึกเฉพาะ reference; **ห้ามใช้ลิงก์สาธารณะกับเอกสารลับ** และต้องทดสอบการถอนสิทธิ์
4. **R3 แจ้งเตือน:** ส่งเฉพาะเหตุการณ์ที่มีสิทธิ์และยินยอม, ใช้ queue/digest/deduplication, งด broadcast ทุกการแก้ไข; วัดปริมาณ Edge/Realtime ก่อนเปิด
5. **ออกแบบโปรเจกต์:** ใช้ project Meeting เดิม ไม่สร้างโปรเจกต์ใหม่เพื่อแยกแต่ละหน้า; หากจะใช้โปรเจกต์ Supabase เดียวกับระบบอื่น ต้องทำ threat model/role separation ก่อน และทบทวนโควตารวม
6. **ข้อมูลคงอยู่:** ห้ามลบมติ รายงานประชุม งาน/หลักฐาน และ audit_events เพียงเพื่อให้ตัวเลขลดลง; กำหนดระยะเวลาจัดเก็บ/การลบตามนโยบายเอกสารราชการและ PDPA เท่านั้น

## 6. การสำรองและกู้คืน (release gate)
- [ ] กำหนดผู้รับผิดชอบและสถานที่เก็บ **backup แบบเข้ารหัส/จำกัดสิทธิ์** นอก public GitHub
- [ ] จัดตารางสำรองฐานข้อมูลด้วยวิธีที่ Supabase รองรับ (เช่น pg_dump จาก environment ที่เชื่อถือได้) และสำรองไฟล์ private Storage/metadata ตามที่จำเป็น; อย่าเข้าใจว่า JSON export บนหน้าเว็บแทน full backup ได้
- [ ] สำรองก่อน migration ทุกครั้ง และกำหนดความถี่เป็น **อย่างน้อยรายสัปดาห์ระหว่างทดลอง**; ก่อนใช้งานจริงต้องกำหนด RPO/RTO และความถี่ตามความเสี่ยงและนโยบายโรงเรียน
- [ ] ทดลอง restore ในสภาพแวดล้อมทดสอบที่ปลอดภัย ตรวจสิทธิ์ RLS, ความครบถ้วนและความสัมพันธ์ของข้อมูล และลงบันทึกผล
- [ ] ให้ผู้บริหารอนุมัติ policy เก็บรักษา/ลบข้อมูลและรับรองการทดสอบสำรองข้อมูลก่อนข้อมูลประชุมจริงเข้าสู่ระบบ

## 7. เกณฑ์ก่อนเปิดใช้จริงและความรับผิดชอบ
- [ ] **R2:** ผ่าน multi-user Auth/RLS/Storage, redirect login, revocation, PDPA, backup/restore
- [ ] **Free-capacity gate:** ยืนยันค่า Usage ใน Dashboard ล่าสุด; ทุกมิเตอร์สำคัญมี owner/วิธีติดตาม; ไม่มีรายการ Unknown ที่กระทบการเปิดใช้
- [ ] **Availability gate:** ยอมรับความเสี่ยง Free ถูกพัก; จัดคู่มือเปิดใช้งานใหม่และวิธีบันทึกกรณีระบบเข้าไม่ได้
- [ ] **R3:** ยังไม่เปิดส่งเตือนจริงจนกว่าจะผ่านสิทธิ์ผู้รับ, dedupe, quota monitoring และทดสอบส่งจริง
- [ ] บันทึกการตัดสินใจว่าจะใช้ Free ต่อ, ลดการใช้ทรัพยากร, หรือขออนุมัติค่าใช้จ่าย Pro **ก่อน** เสี่ยงกระทบงานประชุม

เจ้าของงานเริ่มต้น: ผู้ดูแลระบบ/ผู้บริหารโรงเรียน; ผู้รับผิดชอบประจำวันให้แต่งตั้งในแผนดำเนินงานก่อนเปิดใช้งานจริง

**บันทึกสถานะ:** เอกสารนี้เป็น guardrail และ checklist; ยังไม่มีระบบอัตโนมัติป้องกัน quota breach, backup scheduler, หรือส่งแจ้งเตือนจาก Supabase จริงจนกว่าจะติดตั้งและทดสอบแยกเป็นงานถัดไป
