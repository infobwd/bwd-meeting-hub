# R2 — คู่มือตั้งค่าระบบใช้งานร่วมกัน (สำหรับผู้ดูแล)
อัปเดต: 10 พฤศจิกายน 2569 | สถานะ: **ติดตั้งฐานข้อมูลและเชื่อมค่าหน้าเว็บแล้ว — ยังไม่เปิดใช้ข้อมูลประชุมจริง**

## ทำไมต้องตั้งค่าก่อน
Repository infobwd/bwd-meeting-hub เป็น public ใช้เก็บซอร์สโค้ดเท่านั้น ข้อมูลประชุมทางการและไฟล์ภายในต้องอยู่ในฐานข้อมูลและ private storage พร้อมตรวจสิทธิ์ที่ฝั่งฐานข้อมูล ไม่เก็บเป็น JSON สาธารณะบน GitHub Pages.

## การแก้ปัญหาลิงก์เชิญเปิด localhost:3000 (ตรวจพบ 10 พ.ย. 2569)

**ยืนยันแล้ว:** ลิงก์อีเมลเชิญของผู้ดูแลคนแรกได้รับการยืนยันโดย Supabase Auth และบันทึกการ sign-in แล้ว แต่หลังยืนยันพาไป `localhost:3000` ซึ่งไม่ใช่เว็บไซต์ที่เข้าถึงได้จากมือถือ. ไม่ต้องส่งคำเชิญซ้ำทันที.

เตรียมโค้ด `activate.html` และ `activate.js` สำหรับการขอลิงก์กู้รหัสผ่านและตั้งรหัสผ่านหลังรับ token จาก Supabase.

**ก่อนใช้หน้า Activate ต้องตั้งค่าจริงตามลำดับ:**

1. ใน GitHub repo `infobwd/bwd-meeting-hub` ไปที่ **Settings → Pages → Build and deployment** เลือก **Deploy from a branch**, branch `main`, folder `/(root)` แล้ว Save. รอจน GitHub Pages แสดงลิงก์ที่เผยแพร่และตรวจว่าหน้า `activate.html` เปิดได้จริง. *ยังไม่ถือว่าเว็บไซต์เปิดแล้วจนกว่าจะตรวจได้*.
2. ถ้า URL ที่ GitHub Pages ยืนยันคือ `https://infobwd.github.io/bwd-meeting-hub/`, ให้เปิด **Supabase → Authentication → URL Configuration** ของโปรเจกต์ Meeting แล้วตั้ง **Site URL** เป็น `https://infobwd.github.io/bwd-meeting-hub/activate.html` และเพิ่ม Redirect URL `https://infobwd.github.io/bwd-meeting-hub/**` (หรือ URL ที่ GitHub Pages ให้จริงหากแตกต่าง). ไม่ใช้ `http://localhost:3000` สำหรับคำเชิญ/กู้รหัสผ่าน.
3. เปิดหน้า `https://infobwd.github.io/bwd-meeting-hub/activate.html` จาก iPhone แล้วกรอกอีเมลที่ได้รับคำเชิญ เพื่อส่งอีเมล **ตั้งรหัสผ่านใหม่** (ไม่ต้องส่งคำเชิญซ้ำ เพราะยืนยันบัญชีแล้ว).
4. เปิดลิงก์จากอีเมลกู้รหัสผ่านฉบับใหม่ที่พาเข้าหน้า `activate.html` ตั้งรหัสผ่านอย่างน้อย 12 ตัวอักษร จากนั้นใช้หน้า `workspace.html` เข้าสู่ระบบ.
5. ตรวจสถานะ Auth และสิทธิ์ผู้บริหารอีกครั้ง รวมถึงทดสอบเบราว์เซอร์และมือถือก่อนเปิดใช้งานข้อมูลจริง.

**ข้อควรระวัง:** ห้ามคัดลอกหรือนำลิงก์ในอีเมลที่มี token มาแชร์ในแชต/Repository และห้ามใส่รหัสผ่านหรือ Secret Key ลง GitHub. หน้า R1 ยังเป็นเพียงต้นแบบทดลอง. ไม่มีระบบอีเมลเชิญหรือการกู้รหัสผ่านแบบผู้ดูแลอัตโนมัติจาก GitHub.

- supabase/migrations/202611100001_core.sql: ตารางและความสัมพันธ์
- supabase/migrations/202611100002_security.sql: กฎ RLS ปิดการเขียนตรงจากหน้าเว็บ
- supabase/migrations/202611100003_operations.sql: RPC ตรวจสิทธิ์และบันทึก audit
- supabase/migrations/202611100004_private_evidence.sql: private bucket meeting-evidence, PDF/รูปขนาดไม่เกิน 10MB

หากใช้ CLI: ติดตั้ง Supabase CLI, ใช้คำสั่ง supabase login, supabase link --project-ref PROJECT_REF และ supabase db push ภายใต้บัญชีโครงการของโรงเรียน. อย่า commit access token, database password หรือ service-role/secret keys.

**สำคัญ:** หลังติดตั้งต้องทดสอบสิทธิ์จริงใน staging ก่อนเพิ่มบุคคลหรือเอกสารจริง ไม่ใช่เห็นเว็บแสดงผลแล้วถือว่าปลอดภัย.

## 3) สร้างผู้ดูแลคนแรก
ใช้ Supabase Auth dashboard เชิญผู้ใช้ และให้ผู้ใช้ตั้งรหัสผ่านก่อน. รหัสบัญชีตรงกับ auth.users.id
จากนั้นรันคำสั่งต่อไปนี้ใน SQL Editor ส่วนตัว โดยแทนค่าอีเมลด้วยบัญชีจริง:

~~~sql
insert into public.workspace_members(user_id,role,active)
select id,'admin',true from auth.users
where email='REPLACE_WITH_ADMIN_EMAIL'
on conflict(user_id) do update set role='admin',active=true;
~~~

**ตรวจสอบว่ามี 1 แถวจริง** ก่อนดำเนินการต่อ. อย่าใส่ชื่อหรืออีเมลจริงใน GitHub. ผู้ใช้อื่นต้องสร้างใน Auth และเพิ่มเป็น secretary, member หรือ guest ใน workspace_members ด้วยวิธีผู้ดูแลเท่านั้น. การมีบัญชี Auth อย่างเดียว **ไม่มีสิทธิ์ดูประชุม**.

สำหรับรอบแรก **การเพิ่มผู้ใช้และเชิญบัญชีภายนอกยังทำที่ Supabase Dashboard**; ในหน้าเว็บเพิ่มผู้เข้าประชุมได้โดยใช้ UUID ของบัญชีที่มีอยู่ ไม่ใช่การส่งอีเมลเชิญอัตโนมัติ.

## 4) เปิดหน้าเว็บ
**ดำเนินการแล้ว:** `config.public.js` มี URL และคีย์แบบ publishable ของโปรเจกต์ Meeting (ไม่ใช่ Secret Key) ตัวอย่างสำหรับโปรเจกต์อื่น:

~~~js
window.BWD_SUPABASE_CONFIG = {
  url: "https://YOUR_PROJECT.supabase.co",
  publishableKey: "YOUR_PUBLIC_PUBLISHABLE_KEY"
};
~~~

โปรเจกต์อาจใช้ publishable key รูปแบบใหม่หรือ legacy anon key ทั้งสองเป็น public client credentials ที่อนุญาตได้ **เฉพาะเมื่อ RLS ได้ทดสอบแล้ว** ไม่ใช่การป้องกันข้อมูลโดยตัวมันเอง **ห้ามใช้ service_role หรือ secret key** ในไฟล์นี้.

หน้า `workspace.html` พร้อมเชื่อม Supabase และมีบัญชีผู้บริหารที่ยืนยันคำเชิญแล้ว แต่การตั้งรหัสผ่านและทดสอบเข้าระบบจริงยังไม่ครบ; R1 ใน `index.html` ยังเป็น localStorage demo แยกจาก R2. โปรดตรวจการเข้าสู่ระบบจริงก่อนนำข้อมูลราชการเข้าใช้งาน.

## 5) ตรวจรับสิทธิ์ก่อนเปิดใช้งาน
ใช้บัญชีทดสอบอย่างน้อย 5 บทบาท: admin, secretary/editor, attendee, assigned-only, guest และบัญชีที่ยังไม่เป็นสมาชิก.
- [ ] บัญชีที่ไม่อยู่ใน workspace_members เห็นข้อมูล 0 รายการและเขียนไม่ได้
- [ ] guest เข้าถึงได้เฉพาะการประชุมที่เชิญ ไม่มีสิทธิ์แก้ไข
- [ ] attendee อ่านได้อย่างเดียว ไม่สามารถเพิ่มวาระหรืออนุมัติงานโดยเรียก RPC ตรง
- [ ] editor แก้เฉพาะการประชุมที่ได้รับบทบาท editor และมอบหมายงาน
- [ ] เจ้าของงานเห็นงานแม้ไม่ได้รับสิทธิ์อ่านการประชุม แต่ไม่เห็นรายละเอียดการประชุมที่ไม่ได้รับเชิญ
- [ ] เจ้าของงานส่งสถานะและหลักฐานได้ แต่ตรวจรับงานตนเองไม่ได้หากไม่มีสิทธิ์ editor
- [ ] reviewer ตรวจรับหรือส่งกลับแก้ไขได้เฉพาะงานในประชุมที่ตนเป็น editor
- [ ] เปลี่ยน version เก่าต้องได้ Version conflict ไม่เขียนทับข้อมูลใหม่
- [ ] รายงานประชุมส่งตรวจแล้วล็อกการแก้ไข; admin ตรวจทานหรือส่งกลับได้
- [ ] ทุกเอกสารที่แนบอยู่ใน private bucket และผู้ไม่มีสิทธิ์ดาวน์โหลดไม่ได้
- [ ] ผู้ใช้ทั่วไปไม่สามารถเขียนตารางโดยตรงผ่าน PostgREST
- [ ] ทดสอบเชื่อมงานเดิมเข้าสู่การประชุมอื่น โดยไม่เกิดงานซ้ำ
- [ ] ทดลองถอนสมาชิกแล้วการอ่านและดาวน์โหลดต้องถูกปฏิเสธ
- [ ] ตรวจ audit_events บันทึกผู้เปลี่ยนงาน ผู้ตรวจรับ และการเพิ่มสิทธิ์

## 6) ขอบเขตที่มีแล้ว / ยังไม่มี
**มีโค้ดรองรับ:** Auth, membership + RLS, อ่านจากฐานข้อมูลกลาง, ร่างประชุม/เพิ่มวาระ, บันทึกข้อสรุป, รายงานฉบับร่าง/ส่งตรวจ/ผู้บริหารตรวจทาน, งานมอบหมาย/ส่งตรวจ/ตรวจรับ/ส่งกลับ, ความต่อเนื่องงานข้ามประชุม, ไฟล์หลักฐานส่วนตัว, optimistic version, audit, พิมพ์รายงานเป็น PDF ผ่านเบราว์เซอร์

**ยังไม่ทำ:** การเชิญโดยส่งอีเมลอัตโนมัติ, ตรวจรับล็อกอินจริงครบทุกบทบาทและตั้งค่า redirect เว็บไซต์ที่เผยแพร่, UX มือถือกับผู้ใช้จริง, การลบหลักฐานตามนโยบาย, เชื่อม Google Drive/Google Docs โดยตรง, ระบบแจ้งเตือนจริง (R3), การรับรองมติทางกฎหมายหรือกระบวนการรับรองโดยคณะกรรมการ

### หมายเหตุสำหรับการตรวจทานรายงาน
ปุ่ม "ยืนยันตรวจทาน" สำหรับ admin เป็นเพียงการตรวจทานภายในระบบ ไม่เท่ากับการรับรองรายงานโดยคณะกรรมการสถานศึกษาตามขั้นตอนราชการ ต้องนำเรื่องรับรองเข้าสู่การประชุมตามปกติ.

### ความเสี่ยงของ CDN
หน้า R2 ใช้ supabase-js@2 ผ่าน CDN ก่อนใช้จริงควร pin รุ่นและตรวจสอบนโยบาย supply chain ของโรงเรียน รวมถึงตั้งค่า CSP.

## 7) เปิดใช้เป็นลำดับ
1. ติดตั้ง staging และทดสอบ RLS ด้วยบัญชีจำลอง
2. ทำ UAT ครูและกรรมการ ตรวจความเหมาะสมของภาษาไทย
3. ยืนยัน backup/restore และผู้ดูแลอย่างน้อย 2 คนตามนโยบาย
4. จึงเริ่มข้อมูลประชุมจริงใน private project และปิดความเสี่ยงจากการนำ R1 localStorage ไปใช้ผิดวัตถุประสงค์
