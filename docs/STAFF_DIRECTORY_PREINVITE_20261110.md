# BWD Meeting Hub — ทะเบียนครูเพื่อเตรียมเชิญ (ยังไม่เชิญ)
วันที่: 10 พฤศจิกายน 2569 | ระบบ: Supabase **Meeting**

## สถานะข้อมูลจริง
- เก็บทะเบียนรายชื่อครู 10 คน (หมายเลขทะเบียน 2–11) ในตาราง **`private.staff_directory`** แล้ว
- ใช้ข้อมูลจากผู้บริหารโรงเรียน โดยเก็บชื่อ อีเมลหลัก และอีเมลสำรอง (อีเมลสำรองต้นฉบับ) แยกกัน
- ทุกระเบียนมี `invitation_status = 'not_invited'`; ไม่มีการสร้างบัญชี Supabase Auth, เพิ่ม workspace_members หรือส่งอีเมลใด ๆ
- มี **2 รายการ** ที่ `contact_review_status = 'needs_confirmation'` เพราะรูปแบบอีเมลสำรองน่าสงสัย (โดเมนที่น่าจะพิมพ์คลาดเคลื่อน / มีช่องว่างกลางอีเมล)
- รายการอื่นเป็น `format_ok_unverified` หมายถึงตรวจได้เพียงรูปลักษณ์ ไม่ได้รับรองว่าอีเมลใช้งานได้จริง

## ความปลอดภัยและที่จัดเก็บ
- **ห้ามบันทึกชื่อ/อีเมลรายบุคคลใน GitHub ที่เป็น public**: SQL migration นี้มีเฉพาะ schema, ไม่มีไฟล์ seed ข้อมูลจริง
- ตารางอยู่ใน **private schema** ที่ต้องไม่เปิดให้ Supabase Data API เข้าถึง
- RLS เปิดและไม่มี policy; revoke privileges ของ public, anon, authenticated และ service_role (จัดการได้เฉพาะจากช่องทางฐานข้อมูลที่มีสิทธิ์สูง)
- รายชื่อที่ยังไม่เชิญ **ไม่เท่ากับ** `auth.users`, `public.profiles` หรือ `public.workspace_members` จึงไม่มีสิทธิ์เข้าระบบหรืออ่านการประชุม
- อีเมลสำรองเป็นเพียงช่องทางติดต่อสำรอง **ไม่ถือเป็นบัญชีล็อกอินหรืออีเมลที่ต้องส่งคำเชิญ**

## แนวทางการเชิญในอนาคต (ต้องได้รับคำสั่งชัดเจนก่อน)
1. ผู้บริหารตรวจสอบอีเมลสำรองที่มีสถานะต้องยืนยันและตรวจสอบอีเมลหลักก่อนเชิญ
2. กำหนดบทบาทและขอบเขตสิทธิ์ของแต่ละคน (เช่น member/secretary) โดยการตัดสินใจของผู้บริหาร
3. อนุมัติการส่งคำเชิญรายบุคคล/เป็นชุดอย่างชัดเจนก่อนเรียก Supabase Auth
4. เมื่อมีบัญชีจริง จึงผูก `auth_user_id`, บันทึกเวลาเชิญ และเพิ่ม workspace membership ตามสิทธิ์ที่อนุมัติ
5. ตรวจสอบว่าไม่มีสิทธิ์เข้าถึงการประชุมหรือข้อมูลงานเกินกว่าที่ได้รับมอบหมาย

## ตรวจรับ 10 พฤศจิกายน 2569
- บันทึกครบ 10 รายการ (หมายเลข 2–11)
- 10 รายการยังไม่เชิญ, 0 รายการผูก `auth_user_id`
- 2 รายการต้องตรวจสอบรายละเอียดอีเมล
- สิทธิ์อ่านจาก `anon`, `authenticated`, `service_role` เป็น false ทั้งหมด
- บัญชีจริงใน Supabase Auth ยังคงมีเพียงบัญชีผู้บริหารเดิม 1 บัญชี; ไม่มีการเพิ่มผู้ใช้งานระหว่างการนำเข้าทะเบียน

## หมายเหตุการพัฒนาภายหลัง
หากต้องการหน้าเว็บสำหรับผู้บริหารในการดู/แก้ไขทะเบียน ต้องสร้าง API/RPC ฝั่งเซิร์ฟเวอร์ที่อนุญาตเฉพาะผู้บริหาร พร้อม audit และตรวจสิทธิ์; **อย่า**เปิดตารางนี้จากหน้า GitHub Pages ด้วย publishable key.
